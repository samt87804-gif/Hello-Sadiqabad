**Status:** Proposed plan — awaiting explicit owner approval before implementation

## 1. Owner's goal

For every eligible business published in Hello Sadiqabad:

1. When a person shares its profile link through WhatsApp, Facebook, Messenger, SMS, or another supported platform, the link should produce a rich preview card containing the actual business photo (when available), business name, a short description, and its canonical Hello Sadiqabad URL.
2. When someone searches Google for that business name, the individual Hello Sadiqabad business profile should be eligible to appear as a result, with a relevant title, description, image where Google chooses to show one, and a link to that business's page.

The result should establish Hello Sadiqabad as the directory source for each listing, not falsely claim that the directory owns or operates the listed business.

- Business detail currently calls `updatePageSeo()` with the business's custom SEO title/description where available, a generated fallback, cover/logo image, canonical route, and `buildLocalBusinessJsonLd()`.
- `src/lib/seo.ts` already creates title, description, canonical, Open Graph/Twitter metadata and LocalBusiness + BreadcrumbList JSON-LD in the browser.
- The dynamic `/sitemap.xml` Pages Function already includes all published business slugs.
- Cloudflare Pages crawler handlers already exist for News and Authority Profile pages. They inject page-specific Open Graph/Twitter metadata into HTML for social crawlers and Googlebot.

All 223 lacked custom per-record SEO title/description fields, although generated fallback metadata already exists. These figures are a dated audit snapshot, not a promise about current counts.

## 3. Feature A — Rich business share preview cards

### Expected user experience

When a user shares a URL such as:

`https://hellosadiqabad.com/business/example-business`

the platform should be able to fetch the URL and construct a preview similar to:

- Business cover/profile photo
- Business name as the preview headline
- Short, useful business description
- Hello Sadiqabad as the directory/source
- The canonical business profile URL

This is a link preview generated by the receiving platform from page metadata. It is different from attaching an image file directly to a message. Copy-link, WhatsApp and Facebook sharing will continue to share the canonical URL; the platform should fetch the page's metadata to display the preview.

### Implementation scope

1. Add a Cloudflare Pages Function for `/business/:slug`, following the deployed News and Authority crawler-handler pattern.
2. For recognized social crawlers (WhatsApp, Facebook, Messenger, X/Twitter, LinkedIn, Telegram, Discord, Slack, Pinterest and other verified agents), fetch only the matching **published** business's approved public fields using the existing Supabase publishable key and public RLS.
3. Return the normal application page with business-specific server-visible HTML metadata:
   - `og:title`
   - `og:description`
   - `og:type`
   - `og:site_name`
   - `og:url`
   - `og:image` and `og:image:alt`
   - Twitter `summary_large_image`, title, description and image
   - Canonical URL
4. Image priority: actual business cover/profile image, then actual business logo, then the Hello Sadiqabad site logo as an explicitly branded fallback. Never invent or generate a fake business photo.
5. Ensure image URLs are absolute HTTPS URLs, publicly fetchable without authentication, and point to an image representing that business. Do not publish private storage objects or owner-only photos.
6. Use a concise description from the approved public business description; fall back to factual generated wording from verified public fields only.
7. Keep ordinary visitor routing and the existing ShareSheet actions working unchanged.
8. Add safe HTML escaping, slug validation, response-size bounds, cache headers and failure fallback. A metadata lookup failure must not break the normal business page.
9. Review whether to add a separate “share image” download/file attachment option only if the owner wants an actual image file in addition to the link preview. This is optional and not required for rich URL cards.

### Image readiness

The prior data audit found that 222 of 223 published businesses had no logo or cover image. Therefore:
- Businesses with a real public image can show that image in their preview.
- Businesses without one will show the Hello Sadiqabad fallback logo until a real image is supplied.
- Add an admin/owner profile-completeness workflow or guidance for uploading a business logo/cover using existing authorized upload flows.
- Do not bulk-assign generic stock images or copy photos from Google Maps without checking source rights and permission.
- Do not change existing business records or storage permissions in bulk.

## 4. Feature B — Google organic Search result for each business

### Exact clarification from the owner

The target is a **normal, organic Google Search website result** for each eligible Hello Sadiqabad business profile. For example, searching for “Al-Madina Medical Store Sadiqabad” should make this page eligible to appear as a conventional blue-link result:

- **Search result title:** Al-Madina Medical Store — Sadiqabad | Hello Sadiqabad
- **Displayed URL:** https://hellosadiqabad.com/business/al-madina-medical-store
- **Snippet/description:** Al-Madina Medical Store, Sadiqabad. Contact details, location, opening hours and business information.

This is the directory's own web page appearing in Google's ordinary organic Search results. **It does not mean creating or managing a Google Business Profile, adding every business to Google Maps, creating map pins, or promising a Maps/local-pack listing.** Those are explicitly outside this project scope.

### Expected search result

For a search such as `[Exact Business Name] Sadiqabad`, Google should be able to discover and understand the matching public URL:

`https://hellosadiqabad.com/business/[business-slug]`

A potential result could use a title like:

`Business Name — Sadiqabad | Hello Sadiqabad`

and a short description drawn from the actual listing. Google decides whether and when to show the page, which title/snippet/image it selects, and its ranking.


### Implementation scope

1. **Crawler-facing business HTML:** Extend the business Pages Function so Googlebot receives accurate, page-specific title, description, canonical URL, Open Graph/Twitter metadata and JSON-LD without relying only on browser-side React effects.
2. **Visible useful page content:** Confirm that the normal public business page visibly renders the business name, category, area, verified description, available address/hours/services and useful contact/action details. Search metadata must describe content that real visitors can see.
3. **Unique titles and descriptions:** Generate concise, non-duplicated title and description from the business name, accurate category/area and real description. Prefer owner/admin-supplied SEO fields when present. Do not keyword-stuff or invent services.
4. **Canonical and index policy:** Every published business gets one self-referencing canonical URL. Published, useful profiles may be indexable. Draft, pending, rejected, inactive or otherwise non-public listings must never be exposed by the crawler endpoint or indexed. Confirm redirects and not-found behavior for invalid/unpublished slugs.
5. **LocalBusiness structured data:** Add/serve JSON-LD for the specific listing using verified fields only:
   - Business name and URL
   - Most specific supported business subtype only when confidently mapped from the real category
   - Actual public image URL(s)
   - Accurate Sadiqabad / Punjab / Pakistan address fields, including street address only if available
   - Phone, opening hours, geo coordinates, price range and other properties only when verified and publicly displayed
   - BreadcrumbList linking Home, relevant category (when available), and business profile
6. Do not invent ratings, reviews, addresses, hours, coordinates, phone numbers, official website claims or business-owner relationships. Markup must match visible page content and comply with Google's structured-data guidelines.
7. **Sitemap:** Keep every eligible published business URL in the existing dynamic sitemap; verify new/updated business URLs, canonical host and last-modified handling. Do not add private/admin routes.
8. **Internal linking:** Ensure each eligible business is discoverable through relevant category, area, search and related-business pages. Improve useful links without generating empty doorway pages.
9. **Image SEO:** Use descriptive, accurate image alt text; keep public image URLs crawlable and fast; use real business image assets where available.
10. **Index monitoring:** Use the already-verified Search Console property and submitted sitemap. Inspect a representative sample of business URLs, request indexing for priority pages when appropriate, and monitor Page Indexing, impressions, clicks, queries and crawl errors.

## 5. Google organic Search — important limits and scope distinction

- This work targets conventional organic Google Search website results for the Hello Sadiqabad business URLs. It makes each public business page technically discoverable and eligible for indexing; it cannot force Google to index every URL, show it for every exact-name search, select the exact title/snippet, or rank it first.
- Google Maps listings, Google Business Profile creation/management, map pins and local-pack placement are not deliverables and will not be attempted as part of this feature.
- A sitemap helps Google discover URLs but does not guarantee indexing or ranking.
- LocalBusiness structured data helps Google understand the listing and may make a page eligible for supported search features; it does not guarantee a rich result or Knowledge Panel.
- A Hello Sadiqabad directory page appearing in ordinary organic Google Search is independent of whether that business has a Google Business Profile or Google Maps listing. This project does not require either.
- Do not buy clicks, searches, backlinks or reviews, and do not use automated search manipulation.

## 6. Data, privacy and security requirements

- Use only published public business fields allowed by current Supabase RLS. Never use service-role credentials in the Pages Function.
- Do not expose owner-private contact details, private notes, draft data, moderation records or unpublished photos.
- Validate slugs and use parameterized URL construction; escape all HTML metadata and JSON-LD values.
- Do not change storage policies or make private buckets public to solve image previews.
- Keep existing routes, business data, sharing actions, analytics counters, permissions and owner workflows intact.
- Cache public metadata briefly and safely; account for edits, image changes, unpublishing and stale social-platform preview caches.
- If a listing has incomplete facts, omit unsupported structured-data properties rather than filling gaps with guesses.

| Phase | Work | Acceptance criteria |
|---|---|---|
| 0 — Re-audit | Inspect current business schema, public RLS/view, image storage paths, business fields, Pages routing, sitemap and existing tests | Exact safe public field set and crawler route behavior documented; no assumptions about private data |
| 1 — Share cards | Build `/business/:slug` crawler metadata handler and test helpers | Published business crawler request returns HTTP 200 and correct unique OG/Twitter/canonical metadata; image URL is HTTPS and fetchable; invalid/unpublished listing does not leak data; normal visitor route remains intact |
| 2 — Social verification | Test WhatsApp/Facebook/LinkedIn crawler user agents, image fetch, cache behavior and platform debuggers | Correct business-specific card preview verified on crawler responses; actual platform/device preview recorded separately because platforms cache previews |
| 3 — Google SEO | Improve business title/description, canonical, crawler HTML, JSON-LD and visible-content parity | Sample published business pages return correct title/description/canonical and valid JSON-LD; invalid/private records are excluded |
| 4 — Discovery | Verify sitemap inclusion, robots access, internal links and image crawlability | All eligible published business URLs appear once in sitemap; no private URLs; sitemap response remains valid |
| 5 — Data readiness | Admin/owner image guidance and prioritized correction of missing descriptions/images/addresses | No invented data; owners/admins can provide genuine photos and factual corrections; missing fields are reported transparently |
| 6 — Google monitoring | URL Inspection sample, indexing requests and Search Console follow-up | Record Google-discovered/indexed status and performance only from actual Search Console evidence; do not claim guaranteed rankings |

For every phase, report separately: implemented, automated tests passed, CI passed, deployed, endpoint verified, actual social-platform verified, Google Search Console observed, and owner-confirmed. A successful build alone does not complete a phase.
